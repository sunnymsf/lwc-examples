### Overview

Text date inputs are used for single-line freeform data entry that accepts a valid [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601) date.

### Use Cases

Text date inputs enables an implementer to capture a date consisting of the month, day, and year. These inputs may or may not be part of a larger form, and can be extended as part of a larger component.

### Non-goals

- Complex or composite inputs.
- The resulting value includes the year, month, and day, but not the time
- Does not include a date-picker interface
- Customizations can be made through Styling Hooks and `::part` API, where the addition of CSS through ::part falls outside the support matrix of SDS.
- Variants are not included in SDS. Variants should be applied at the subsystem layer.

### Features

- The API design of the SDS Input Date is specific to the [HTML Input Date](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input/date) element.
- The resulting value includes the year, month, and day, but not the time.
- Defaults the date to todays date
- Support internationalization (i18n) and localization (l10n) through the [Intl.DateTimeFormat](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/DateTimeFormat) API.
- Support for [ISO 8601](https://en.wikipedia.org/wiki/ISO_8601) date format.
- Validates the date entered by the user, ensuring ISO 8601 format.
- Manual date input and validation is supported.
- The default appearance provides the basic structure of a text input date.
- The default appearance comes unbranded.
- Styling Hooks should be used to customize the appearance.
- Customization beyond Styling Hooks can be achieved through the CSS Shadow Parts API.

### API

The API design that follows _only_ applies to the [HTML Input Date](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input/date).

### Custom Element

This specification will apply to a SDS custom element but can also be implemented in a subsystem's ecosystem with the subsystems namespace used as the prefix to the custom elements definition:

1. `sds-input-date` - This is owned by the Salesforce Design System (SDS) Team.
2. `<namespace>-input-date` - This is owned by a subsystem built on SDS, e.g. `dxp-input-date`

### Anatomy and Appearance

#### DOM Structure

```html
<host>
  <div part="input-date">
    <div part="label-container">
      <slot name="label-start"></slot>
      <label part="label">
        <slot name="label"></slot>
      </label>
      <slot name="label-end"></slot>
    </div>
    <div part="input-container">
      <slot name="start"></slot>
      <input part="input" />
      <slot name="end"></slot>
    </div>
  </div>
  <div part="help-text">
    <slot name="help-text"></slot>
  </div>
</host>
```

#### Slots

| Slot Name | Description | Fallback Content |
| - | - | - |
| `label` | Text content that describes the input | empty |
| `label-start` | Content placed prior to the user-added text, such as an icon | empty |
| `label-end` | Content placed after to the user-added text, such as an icon | empty |
| `start` | Content placed prior to the user-added text, such as an icon | empty |
| `end` | Content placed after to the user-added text, such as an icon | empty |
| `help-text` | Content area for additional text, such as examples of the type of required data entry, or error messages | empty |

#### Parts

| Part Name | Description |
| - | - |
| `input-date` | Enables styling for the entire component beyond Styling Hooks, falls outside the support matrix of SDS |
| `label` | Enables styling for the label beyond Styling Hooks, falls outside of the support matrix of SDS |
| `input-container` | Enables styling for the input and corresponding `start` and `end` slots, falls outside of the support matrix of SDS |
| `input` | Enables styling for the input itself beyond Styling Hooks, falls outside the support matrix of SDS |
| `help-text` | Enables styling for the help-text itself beyond Styling Hooks, falls outside the support matrix of SDS |

### Behavior

#### States & Interactions

| State Group | States | Initial State | Description|
| - | - | - | - |
| `focus` | `false` | `false` | When the input receives focus. It is generally triggered when the user clicks or taps on an element or selects it with the keyboard's Tab key. |
| `disabled` | `true`/`false` | `false` | Indicates whether the input is disabled and cannot be interacted with. When disabled, the control is not included in form validation |
| `readonly` | `true`/`false` | `false` | Controls whether or not the user can edit the form control |
| `active` | `true`/`false` | `false` | Controls whether or not the user is currently typing in the form control |

### Accessibility

All [global `aria-*` attributes](https://www.w3.org/TR/wai-aria-1.1/#global_states) should follow all [interaction requirements](https://developer.mozilla.org/en-US/docs/Web/HTML/Element/input) per the W3C.

When interacting with the associated label via click, it should focus the related input.

### Internationalization

The input date component supports internationalization (i18n) and localization (l10n) through the [Intl.DateTimeFormat](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/DateTimeFormat) API

All elements of the input control (e.g., `start`/`end` slots, user-entered text, icons, etc) should adhere to bi-directional languages such as `ltr` (left to right) and `rtl` (right to left).

### Test Plan

- All inputs should have visual regression tests to catch any unintended modifications to the visuals.
- All inputs should have unit tests to ensure the correct input and output of attributes, states, and events.
- All inputs should test for color contrast combinations that, at a minimum, fulfill the requirements of WCAG 2.1.
- All inputs should be tested across all supported devices, ensuring that modifications for mobile are taken into account.
