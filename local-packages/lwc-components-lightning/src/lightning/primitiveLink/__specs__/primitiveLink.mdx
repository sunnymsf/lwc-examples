### Overview

An interactive reference to an internal or external resource that, when activated, causes the user agent to navigate to that resource.

### Use Cases

The link enables an implementor to create a simple, but customizable link element.

### Non-goals

- Complex or composite links.
- Customizations can be made through [Styling Hooks][styling-hooks-jump] and `::part` API, where the addition of CSS through `::part` falls outside the support matrix of SDS.
- Variants are not included in SDS. Variants should be applied at the subsystem layer.

### Features

- The CSS can be used on a set of [interactive content](https://html.spec.whatwg.org/multipage/dom.html#interactive-content-2) to represent the appearance of a link:
  - `a` - [WHATWG Spec][anchor-spec]
- The API design of the SDS Link is specific to the [HTML Link][anchor-spec] element and should not be implemented on any other HTML element. All methods and properties pertain to the HTML element as it was designed by the web platform.
- The "default" appearance provides the basic structure of a link.
- The "default" appearance comes unbranded.
- [Styling hooks][styling-hooks-jump] should be used to customize the appearance of the link.
- Customization beyond Styling Hooks can be achieved through the [CSS Shadow Parts API][css-shadow-parts]. The addition of CSS is allowed through `::part` but falls outside the support matrix of SDS.

### API

The API design that follows _only_ applies to the [HTML a[href] Element][anchor-spec].

The SDS link component should support all methods and attributes of the [HTML a[href] Element][anchor-spec].

#### Custom Element

This specification will apply to a SDS custom element but can also be implemented in a subsystem's ecosystem with the [subsystems namespace][namespace-service] used as the prefix to the custom elements definition:

1. `sds-link` - This is owned by the Salesforce Design System (SDS) Team.
2. `<namespace>-link` - This is owned by a subsystem built on SDS, e.g. `dxp-link`

### Anatomy and Appearance

The following DOM structure and named part attribute on the leaf node as documented is **required** to use the SDS link CSS.

#### DOM Structure

```html
<host>
  <a part="link">
    <slot name="start"></slot>
    <slot></slot>
    <slot name="end"></slot>
  </a>
</host>
```

#### Slots

| Slot Name | Description | Fallback Content |
| - | - | - |
| `start`   | The content that at the start of the primary link content | empty |
| `default` | The primary link content                                  | empty |
| `end`     | The content that at the start of the primary link content | empty |

#### Parts

| Part Name | Description |
| - | - |
| `link`  | Enables styling beyond Styling Hooks, falls outside the support matrix of SDS |

### Behavior

Please use the following sections to describe the basic intended behavior of the component. This can come in the form of state changes when a user interacts with the component or if the component receives an event.

#### States & Interactions

| State Group | States | Initial State | Description |
| - | - | - | - |
| `hover`    | `hover` | `false` | When a user interacts with link, but does not necessarily activate it. |
| `focus`    | `false` | `false` | When a link receives focus. It is generally triggered when the user clicks or taps on an element or selects it with the keyboard's <kbd>Tab</kbd> key. |
| `active`   | `false` | `false` | When a user activates the link. |
| `disabled` | `true` / `false` | `false` | Indicates whether the link is disabled and cannot be interacted with. |

### Accessibility

#### Truncation

The text within a link should never be truncated. If you are dealing with long text, please wrap the text to a second line.

### Internationalization

All slotted content inside the button should adhere to bi-directional languages such as `ltr` (left to right) and `rtl` (right to left).

### Test Plan

- All links should have visual regression tests to catch any unintended modifications to the visuals of the link
- All links should have unit tests to ensure the correct input and output of attributes and events
- All links should have a test to catch color contrast regressions that, at a minimum, fulfill the requirements of WCAG 2.1.
